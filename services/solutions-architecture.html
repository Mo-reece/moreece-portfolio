What this covers

The expensive decisions are the ones made before any code is written.

Architecture work is useful when a system has to serve more than one audience, hold data that other processes depend on, or integrate with services nobody controls. The goal is a design that states clearly where each responsibility sits, so the build has a shape to follow and the result can be extended later without unpicking it.

In practice this means separating the interface from the services behind it, deciding what the database is the source of truth for, choosing where authentication and payments belong, and being explicit about what happens when an external service is slow or unavailable.

Typical problems addressed

  • Features are being added faster than anyone can explain how the system fits together.
  • Business rules live in several places, so the same question returns different answers.
  • An integration, payment provider, or data source needs replacing without a rewrite.
  • A working prototype has to become something a team can operate and hand over.

Typical deliverables

A design the build can follow.

Deliverables are scoped to the size of the system and who has to maintain it.

System diagram

Components, boundaries, and the direction data moves between interface, services, and storage.

Data model

Entities, relationships, and the record each part of the system is allowed to consider authoritative.

API contract

Endpoints, request and response shapes, authentication, and how errors are reported to callers.

Integration plan

Third-party services, what each is trusted for, and the fallback when one is unavailable.

Environment and deployment

How the system is configured, released, and separated between development and production.

Decision record

The options considered, the choice made, and the constraint that drove it, written down for whoever inherits it.

Workflow

Decide, then build against the decision.

The sequence keeps design ahead of implementation without stalling delivery.

Frame

Establish the users, the decisions the system supports, and the real constraints.

Model

Define the data, the boundaries between services, and the contracts between them.

Prove

Build the riskiest slice first so the design is tested before the rest depends on it.

Hand over

Document the decisions and the operating runbook so the design survives the handover.
